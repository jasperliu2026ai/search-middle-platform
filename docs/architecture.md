# Search Middle Platform 架构说明

## 1. 架构定位

`search-middle-platform` 的定位不是单一搜索脚本，而是一层面向 Agent 的搜索中台。

它处在“用户问题”和“最终搜索答案”之间，负责把原始查询变成一条有结构的搜索执行链路。

核心目标：
- 统一入口
- 分类路由
- 多源搜索
- 去重仲裁
- 答案收敛
- 为后续扩展更多数据源和评分机制预留结构

## 2. 总体架构

整体可以抽象成五层：

1. **入口层**
2. **路由层**
3. **搜索执行层**
4. **仲裁层**
5. **答案层**

对应当前仓库中的主要实现：

- 入口层：`scripts/search_hub.js`
- 路由层：`scripts/search_router_mvp.js`
- 搜索执行层：
  - `scripts/multi_source_search_mvp.js`
  - `scripts/tech_search_mvp.js`
  - `scripts/tech_search_pro.js`
  - `scripts/tech_search_ultimate.js`
  - `scripts/search_multi_source_images.js`
- 仲裁层：`scripts/search_arbiter_mvp.js`
- 答案层：
  - `scripts/search_answer_mvp.js`
  - `scripts/search_answer_nl.js`

## 3. 模块职责

### 3.1 入口层

**模块：** `search_hub.js`

**职责：**
- 接收统一查询输入
- 调起路由逻辑
- 协调整体执行顺序
- 统一输出路径和结果产物

**意义：**
入口层把外部调用方式固定下来，避免每条搜索路线都暴露不同的命令和参数形态。

---

### 3.2 路由层

**模块：** `search_router_mvp.js`

**职责：**
- 判断用户查询属于哪一类问题
- 决定应该走哪条搜索路线
- 将请求分发给技术、通用或图片检索模块

**当前路由类型：**
- `tech`
- `general`
- `image`

**意义：**
这是中台的关键控制点。
如果没有路由层，所有问题都会退化为“统一硬搜”，导致结果质量不稳定。

---

### 3.3 搜索执行层

**模块：**
- `multi_source_search_mvp.js`
- `tech_search_mvp.js`
- `tech_search_pro.js`
- `tech_search_ultimate.js`
- `search_multi_source_images.js`

**职责：**
- 面向不同问题类型执行具体搜索
- 聚合来自不同搜索源的结果
- 输出原始结果集，供后续仲裁与答案层处理

**设计特点：**
- 技术搜索支持分层版本（MVP / Pro / Ultimate）
- 通用搜索承担基础多源聚合职责
- 图片搜索独立成线，避免和文本搜索混在一起

**意义：**
搜索执行层是“能力承载层”，它决定这套中台到底能搜什么、搜得多深、搜得多广。

---

### 3.4 仲裁层

**模块：** `search_arbiter_mvp.js`

**职责：**
- 对搜索结果做基础去重
- 对候选结果做初步筛选和仲裁
- 为答案层提供更干净的输入

**意义：**
搜索不是把所有结果都扔给用户。
仲裁层存在的目的，就是把“结果很多”转成“结果可用”。

**当前状态：**
- 已具备 MVP 级能力
- 后续可以继续增强评分、权重、可信度判断

---

### 3.5 答案层

**模块：**
- `search_answer_mvp.js`
- `search_answer_nl.js`

**职责：**
- 对仲裁后的结果做最终收敛
- 生成更适合直接给用户或上层 Agent 使用的答案
- 在需要时保留原始结果路径，方便排查和复核

**意义：**
答案层是“交付层”。
它决定这套系统最后吐出来的是原始材料，还是可直接消费的答案。

## 4. 数据流

完整数据流如下：

1. 用户输入 Query
2. `search_hub.js` 接收请求
3. `search_router_mvp.js` 对查询进行分类
4. 路由到对应的搜索执行模块
5. 搜索执行模块返回原始结果
6. `search_arbiter_mvp.js` 做去重与仲裁
7. `search_answer_*` 生成最终答案
8. 返回最终结果与原始结果路径

## 5. 分层价值

这套分层不是为了好看，而是为了解决几个实际问题：

### 5.1 降低耦合

把：
- 查询理解
- 搜索执行
- 结果处理
- 最终输出

拆成不同层后，后续改某一层时，不必整个系统一起重写。

### 5.2 便于扩展

未来要新增：
- 新搜索源
- 新路由类型
- 新仲裁规则
- 新答案模板

都可以在现有结构上扩，而不是推倒重来。

### 5.3 便于观测和排障

中台化之后，问题可以更容易定位在：
- 路由错了
- 搜索源质量差
- 仲裁不够强
- 答案层收敛不好

这比“一坨脚本全塞在一起”更好调试。

## 6. 当前已知边界

当前版本仍然是 Beta，边界要说清：

- 分类逻辑仍可继续增强
- 仲裁层还是 MVP 级
- 三条路线输出 schema 还不完全统一
- 公共工具层抽象还不够完整
- 自动化测试仍偏少

也就是说：
它已经是一个能跑的架构骨架，但还不是完全成熟的搜索平台。

## 7. 推荐演进方向

### 7.1 统一输出 Schema

建议为 `tech / general / image` 三条路线定义统一结果结构，例如：
- `route`
- `query`
- `sources`
- `items`
- `final_answer`
- `raw_output_path`
- `confidence`

### 7.2 引入 Source Adapter 抽象

把不同搜索源进一步抽象成统一接口，降低具体实现与路由/仲裁层的耦合。

### 7.3 升级仲裁机制

从“基础去重”逐步升级到：
- source 权重
- 结果可信度
- 多源一致性评分
- 冲突信息识别

### 7.4 增强测试体系

建议增加：
- 路由测试
- schema 测试
- 结果结构测试
- 回归测试

### 7.5 增加可视化观测能力

可以考虑后续增加：
- 每一层的输入输出快照
- 路由命中记录
- 失败节点日志
- 仲裁前后结果对比

## 8. 适合谁接入

这套架构特别适合：
- 有多种搜索任务的 Agent
- 想把搜索能力做成公共能力层的团队
- 需要把技术搜索、通用搜索、图片搜索拆开管理的场景
- 需要在搜索结果之上再做答案生成的系统

## 9. 和 Team Mode 的关系

在 `team-mode-skill` 体系下，`search-middle-platform` 更像搜索能力底座。

典型分工可以是：
- `[阿查]` 负责触发和使用搜索中台做检索
- `[阿干]` 负责把搜索结果转进具体执行流程
- `[阿审]` 负责检查结果质量、噪音、偏题和遗漏
- `[阿总]` 负责根据结果推进任务并对用户交付

## 10. 一句话总结

`search-middle-platform` 的本质，是把 Agent 的搜索能力从“零散脚本”升级成“可路由、可仲裁、可扩展、可交付”的中台骨架。
